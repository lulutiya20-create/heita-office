一、响应速度

高首屏白屏等待云端拉取

页脚主脚本 init() → loadAppAsync() 会先 await tryJsonbin()（网络超时上限 15s）才开始首次渲染。网络慢时用户面对长时间白屏。代码里其实已有本地优先的 loadApp()（注释写明"先用 localStorage 快速渲染，避免白屏"），但 init 没有使用它。

建议：init 改为「先用 localStorage 立即渲染 → 异步拉 JSONBin → 有差异再合并刷新」。首屏可从秒级降到几乎瞬时。
高头部第三方统计脚本阻塞渲染

<script src="https://beacon.cdn.qq.com/sdk/..."> 位于 head 且无 async/defer，是渲染阻塞资源；该 CDN 慢或超时会直接拖慢 LCP。

建议：加 defer（或移到 body 末尾）。一行改动，零风险。
中字体未 preload、格式偏重

5 个 TTF/OTF 字体走 jsDelivr，已设 font-display:swap（好），但主标题字体 JupiterPro 无 preload，TTF 体积比 woff2 大 50%+。

建议：① 对 JupiterPro 加 <link rel="preload" as="font">；② 有空时用 fonttools 转 woff2 并子集化（拉丁字符集很小，预计可减 60% 以上）。
中移动端滚动重绘开销

body 使用 background-attachment:fixed（移动端滚动时反复重绘，低端机明显卡顿），header 使用 backdrop-filter:blur(10px) 且 sticky。

建议：在 @media(max-width:768px) 里去掉 fixed（背景本来就是渐变，滚动时几乎看不出差别）；backdrop-filter 可降为半透明纯色背景。
低图库 / 留言板一次性全量渲染

renderGallery() / renderMessages() 把全部条目拼成一个 innerHTML 一次插入，无分页。图片有 loading=lazy 兜底，几十张没问题，但照片/留言涨到几百条后 DOM 数量与解码压力会显现。

建议：做"加载更多"分页（每页 30~50 条）即可，无需虚拟列表。
低未使用 Service Worker / PWA

纯静态站非常适合加 SW：缓存字体、框架图（frames/）、贴纸等不变资源后，二次打开速度大幅提升，断网也能看缓存内容。

建议：加一个简单的 SW（cache-first 静态资源 + network-first 数据）。注意 GitHub Pages 子路径部署时 base path 要写对。

二、稳定性 / 数据层

高saveLocal 无配额保护

localStorage.setItem(DB_KEY, ...) 没有 try/catch。存量数据含 base64 头像/旧图，一旦超出 5MB 配额会抛 QuotaExceededError，直接中断 saveApp 流程——表现为"点了保存/留言没反应"，且很难排查。

建议：① 包 try/catch + toast 提示；② 做一次性迁移：把存量 base64 头像/事件图转存 GitHub 图床，把 JSON 体积压下来。
中全量 JSON.stringify 对比

轮询与冲突检测用 JSON.stringify(newApp)!==JSON.stringify(app) 全量对比，数据大时（几百 KB）每次变更要序列化两遍。项目里已有 jsonbinFingerprint()，本地对比可以复用同一指纹思路。

建议：本地缓存一份上次指纹做对比，替代双序列化。
低3 秒遮罩保险 watchdog

init 里有一个每 3 秒查询 DOM 的 setInterval，只为兜底关闭异常遮罩。成本很小，但属于常驻轮询。

建议：改为在打开遮罩的函数里记录状态、或用 MutationObserver；不急。
低多设备并发写窗口较大

轮询间隔 30 分钟（受 JSONBin 免费额度约束，48 读/天/设备 ≈ 1440 读/月，在 10k 额度内）。两台设备 30 分钟内同时改动时，靠推送前的"读预检 + 冲突弹窗"兜底，整体是稳的，但窗口偏大。

建议：维持现状即可；若额度富余可降到 10 分钟。推送前的点赞合并（mergeLikeCounts）设计得很好，保留。

三、界面 / 交互

中无 URL 路由（刷新回首页）

navigate() 只切换 DOM 的 active 类，不写 location.hash。刷新后回到首页、无法把"族谱页/图库某相册"链接直接发给别人。

建议：navigate 时写 location.hash，启动时读 hash 恢复页面。改动小、收益大（约 10 行）。
中切回首页总是重建轮播

每次 navigate('/') 都执行 renderCarousel() 重建 track 的 innerHTML 并重启计时器，切页往返时可能闪一下、播放进度重置。

建议：加脏标记：数据没变就跳过重建。
低移动端书签条可能溢出

.bm-nav 为 flex-wrap:nowrap，58px 方块 × N 个，小屏书签超过 5 个就会横向溢出。

建议：小屏允许横向滚动（overflow-x:auto）或换行。
低可访问性欠账

全站仅 3 处 aria-label；头部 ☁/📊 等图标按钮无文字替代；留言板无字数上限提示。整体 contrast 达标，键盘 Esc 关闭遮罩已做（好）。

建议：给图标按钮补 aria-label / title；留言输入加 maxlength（如 500）。

四、代码质量 / 安全

中族谱 SVG 节点成员名未转义

renderFamilyTree() 中节点名称直接插值 ${m.name}（其余字段都走了 esc()）。成员名由管理员设置，风险低，但破坏了全站统一的转义约定。

建议：补一个 esc(m.name) 即可。
低相册 id 拼进 onclick 字符串

onclick="gallerySetView('${a.id}')" 为字符串拼接。id 目前是内部生成的，无实际风险；统一改为 esc 或事件委托更稳。

建议：顺手统一，不急。
低initApiEndpoint 已空转

该函数候选列表为空、永远返回 false，init 每次都 await 它。逻辑无害但属于历史遗留。

建议：可整体删除 /api/data 相关死代码（safeFetchJson 轮询分支、API_DATA 等），减少约百余行维护负担。删除前确认无回退需求。

五、功能增强方向（可选）

· 搜索：成员名录 / 图库 / 留言板加一个前端过滤框（纯前端即可）。
· 留言增强：删自己的留言、留言点赞。
· 灯箱手势：移动端双指缩放 + 左右滑动切图。
· 骨架屏：配合"本地优先渲染"，首屏即使拉云端也无感知。
· 图库分页：与上面"加载更多"合并实现。

六、建议的处理顺序

第一批（小改动、大收益，约半小时）：本地优先渲染（白屏）、beacon 加 defer、saveLocal 加保护、族谱名字转义、hash 路由。
第二批：图库/留言分页、轮播脏标记、移动端背景与书签条适配、图标按钮 aria-label。
第三批（可选）：Service Worker、字体 woff2 子集化、死代码清理、搜索等新功能。
